### M2 refinements

- **B24 (refined):** directories and symlinks to directories are always the Folder category (their extension is ignored, so a folder named `data.json` is a folder); the extension category applies to files, packages and symlinks to files.
- `middleTruncate(text, maxWidth, measure)` takes no `tailBias` argument: for `k` kept characters the head gets `ceil(k/2)` and the tail `floor(k/2)`.
- `lib/selectionReducer.ts` also exports `listTarget`; arrow targets for the Icons view are in `lib/grid.ts`.
- `open_path` moved from M4.4 to M2.2 (M2's acceptance requires opening files). `reveal_in_finder`, `get_info`, `copy_text` and `open_full_disk_access_settings` stay in M4.4.
- `listing.fetch` never commits state: navigation commits listing, `currentPath` and selection in the same tick (`commitSuccess`), so the UI never shows a new path with the old listing.
- **Dev log forwarder (agent smoke runs):** in `tauri dev`, `src/lib/devLog.ts` forwards `window.onerror`, unhandled rejections and `console.error/warn/info` to the Vite dev server (`/__devlog`), which appends them to the file named by `NAVITA_DEV_LOG` (discarded when unset). This is how plan section 5.2 detects `Uncaught` errors, because the Tauri dev terminal does not show the webview console. The code is inactive in production builds (`import.meta.env.DEV`).

### M4 notes

- **Order change:** the Rust commands `reveal_in_finder`, `get_info`, `copy_text` and `open_full_disk_access_settings` landed in the M4.3 commit (with the menu) because the menu actions need them; M4.4 contains the JS context menus.
- **S5 (menu accelerators): not verifiable by the agent.** `osascript` is denied keystroke injection (error 1002) and UI scripting (-1719) in the agent session. The menu builds with every accelerator string accepted (no panic at startup). Whether each chord actually fires is a **[USER] check** (docs/QA.md, M4). Pre-decided fallback: for any chord that does not fire, drop its accelerator from the menu item and handle the chord in `lib/keyboard.ts` via `e.code`, with `preventDefault` (this also suppresses the native menu action, so there is no double firing). WebKit delivers `keydown` for ⌘-chords before the menu sees them, so a chord must never be handled both by the menu accelerator and by `keydown` without `preventDefault`.
- `syncMenu(true)` runs after every menu click: macOS toggles a CheckMenuItem's mark itself, even when the state did not change (e.g. clicking the already checked "as Icons").
- The menu items `file.newFolder`, `file.rename`, `file.trash` exist but stay disabled until M8; `dispatchAction` ignores them until then.
- Sidebar keyboard focus is tracked by row key (`ui.sidebarFocusKey`), not by the current path, because the same folder can appear in several sections (for example "Macintosh HD" in Locations and as the tree root); navigating by "next row after the row whose path is current" would loop.
- Dev log: menu events are logged as `[navita] menu <id>` in `tauri dev` for manual accelerator testing (`NAVITA_DEV_LOG=<file> npm run tauri dev`).
- Context menus are built with `@tauri-apps/api/menu` (`lib/contextMenu.ts`); `core:menu:default` already contains `allow-new`, `allow-popup` and the item permissions. A dev-only self-check (`lib/devSelfCheck.ts`) builds both menus at boot and logs `[navita] selfcheck context menus ok`, because the agent cannot right-click.
- `lib/features.ts` exports `FILE_OPS_ENABLED` (false until M8) which gates Rename… and Move to Trash in the item menu.

- Preferences persist to `~/Library/Application Support/com.sgchris.navita/prefs.json` (`@tauri-apps/plugin-store`, one key per preference, only changed keys are written, debounced 300 ms, flushed on window blur). ### Window must not wait for animation frames (bug found during M6.3)

The window is created hidden (A14). The first version showed it after two `requestAnimationFrame`s, but WebKit does not run animation frames for a hidden window, so the window **never appeared** (CoreGraphics reported the 1100×700 window as `onscreen: false`; `document.visibilityState` stayed `hidden`). Fix (`lib/platform.ts: showWindowOnce`): the window is shown and focused right after the first listing has been committed (plus 30 ms for React to commit), with a 1.5 s safety timer in case the listing is slow or fails. `core:window:allow-set-focus` was added to the capabilities. Verified: CoreGraphics reports the window `onscreen: 1` and `visibilityState` becomes `visible`.

### M6.3 performance results (spec 6.8)

Measured on the development machine (Apple Silicon, macOS 26.6.2, window focused and visible). Rust numbers are from `cargo test --release`; frontend numbers were measured inside the real WKWebView of `tauri dev` (unoptimized React development build, so a release build can only be faster) with a temporary harness that loaded 10,000 synthetic entries (10 % folders, 10 % hidden) into the stores; the harness was removed afterwards. "End to end" values include waiting for two animation frames (about 33 ms at 60 Hz), so the actual work is the value minus roughly 33 ms.

### M8 notes

- **Trash tests:** the gate tests use a fake `Trasher` (so `npm run check` never fills the real Trash); one `#[ignore]`d test (`cargo test real_trash -- --ignored`) moves a uniquely named empty file through the real `NSFileManager` path. It was run once; the empty file `navita-test-<pid>-trash.tmp` stays in the Trash because the agent cannot read `~/.Trash` (TCC) to remove it.
- Name validation reasons: empty -> "A name can't be empty."; `.`, `..` or NUL -> "That name isn't allowed." (not listed in B32); `/` or `:` -> "Names can't contain “/” or “:”."; over 255 UTF-8 bytes -> "Name is too long.". `lib/names.ts` mirrors them exactly.
- `rename_path` returns the new absolute path; renaming to the identical name is a no-op that returns the old path.
- **Rename editor:** Return commits; Esc cancels; blur commits a valid changed name, but blur with an **invalid** name reverts instead of keeping the editor open (so the editor never fights the user for focus); Return with an invalid name keeps editing with a red outline and the reason as tooltip. `Return` outside an editor starts renaming the single selected item; `file.newFolder`, `file.rename` (menu item without accelerator), `file.trash` (`⌘⌫`) are live; while an editor is open only `edit.selectAll` (selects the text) is honoured.
- A rename to a name that becomes hidden (leading dot) while hidden files are off removes the item from view and clears the selection.

### S2 Enter and F2

- **Enter opens the selection** (same as ⌘↓): a single folder or symlink to a folder is entered, every other selected item is opened with its default app (packages such as `.app` launch), folders inside a multi-selection are skipped. This supersedes spec section 9.2 ("Return reserved for rename") and the earlier M8 behavior where Return started renaming.
- **F2 renames** the single selected item (any kind). It is handled in `lib/keyboard.ts` (content pane only, ignored while an editor is open) rather than as a menu accelerator, because menu accelerators are still unverified (spike S5); `File ▸ Rename` and the context menu keep working without a shortcut hint.

### S3 Move to Trash confirmation

- Every Move to Trash asks first, with a native macOS sheet (`@tauri-apps/plugin-dialog` `ask`, plugin pinned to major 2, permission `dialog:allow-ask`): "Are you sure you want to move “name” to the Trash?" (or "these N items") plus "You can restore items from the Trash.", buttons **Move to Trash** / **Cancel**.
- `fileOps.trashSelection()` is the only caller of `trash_paths`, so ⌘⌫, File ▸ Move to Trash and the context menu are all covered. Only an explicit confirmation continues; a dialog that cannot be shown counts as not confirmed (status-bar message), and a flag prevents stacked dialogs.
- `tauri-plugin-dialog` pulls in the `tauri-plugin-fs` crate as a dependency of its file pickers; that plugin is **not** registered and no `fs` permission is granted, so the "no `fs` plugin" rule (all file access in audited Rust commands) still holds.

### S4 New File and creating inside a folder

- New Rust command `create_file(parent)` creates an empty `untitled file` (then `untitled file 2`, …; no extension) with `create_new`, sharing the collision loop (`create_unique`) with `create_folder`.
- `fileOps.createItem(kind, folder?)`: without `folder` (empty-space menu, ⇧⌘N) the item is created in the current folder and renamed in place; with a `folder` (context menu on a folder) it is created inside that folder, then that folder is opened and the new item is selected with its name editor open.
- Context menu layouts: **folder** (single selected folder): Open · New Folder · New File · Reveal in Finder · Copy Path · Get Info · Rename… · Move to Trash; **file / multi-selection**: Open · Reveal in Finder · Copy Path · Get Info · Rename… (single only) · Move to Trash; **empty space**: View ▸ · Show Hidden Files · Sort By ▸ · New Folder · New File. ### S5 ".." row

- List view shows a synthetic **".."** row as the first row of every folder except `/`; Icons view never shows it. It ignores the hidden-files toggle and the sort key/direction, and appears in empty folders too (the empty message is drawn below it). Date and Size show `--`, Kind "Folder".
- It is selectable and focusable (arrow keys pass through it). Enter, ⌘↓ and double-click on it go up (`navigation.up()`, which selects the folder you came from). Right-click on it shows the empty-space menu.
- It is **never an operand of a file operation**: its path is `<folder>/..` (not a real path); `getVisibleEntries()` (real items only) feeds Select All, type-to-select, the status count and every operation (`getSelectedEntries()`), while `getListEntries()/getVisiblePaths()` (with the row) feed rendering, arrow navigation and range selection. The selected count in the status bar and the menu's enabled flags count real items only. A live refresh reconciles the selection on real items and leaves a selection of only ".." alone.
- Type-to-select now selects by path (`selectOnly`) instead of by list index, because list indexes are shifted by the extra row.
- Verified live in `tauri dev`: first row is `..`, Select All has no `..`, Enter on `..` navigated up and selected the child, empty folder shows `..` plus the message, no `..` in Icons view or at `/`.

### S6 Cut / Copy / Paste (system clipboard)

- **Feasible and implemented** with the real macOS pasteboard: `src-tauri/src/clipboard.rs` uses `objc2-app-kit` `NSPasteboard` (file URLs), so files copied in Navita can be pasted in Finder and the other way round. No new permission is needed. Tests use a private pasteboard (`pasteboardWithUniqueName`), never the user's clipboard.
- **Limitation (macOS has no file "cut"):** Cut = copy to the pasteboard + Navita remembers to _move_ on paste. Pasting in Navita moves the files; pasting in Finder or another app copies them. The move only happens if the pasteboard's `changeCount` is unchanged since the Cut (otherwise the paste is a plain copy of whatever is on the clipboard now). Cut items are not dimmed.
- Paste target: right-click a folder → Paste goes **inside that folder**; right-click empty space → Paste goes into the **current folder**. Files only get Cut and Copy. Paste is disabled when the clipboard holds no files.
- `fs/paste.rs`: never overwrites; a name clash (or pasting into the folder the item is already in) becomes Finder-style `name copy.ext`, `name copy 2.ext`, …; copying uses `/bin/cp -c -p -R` (APFS clone when possible, metadata and extended attributes kept, symlinks copied as links); moving uses `renamex_np(RENAME_EXCL)` and, across volumes, copy then delete the source only after a successful copy; moving a protected item is refused; a folder cannot be pasted into itself or a descendant; everything is validated before the first item is touched; moving an item into its own folder is a no-op.
- NSURL spells file names in decomposed Unicode ("U" + combining mark); `paste` resolves each non-symlink source through `canonicalize` (which returns the on-disk spelling) so copies keep the original name form.
- Live check (agent, real app, general pasteboard; the user's clipboard text was saved and restored): copy → pasteboard readable from outside the app via AppleScript, paste into another folder, cut + paste moved a folder and cleared the mark, paste into the same folder produced `a copy.txt` and selected it, a cut followed by an external clipboard change pasted as a copy and left the source in place.

### S7 Image thumbnails

- Image files (extensions `png jpg jpeg gif heic heif webp tiff bmp svg raw cr2 nef dng`, readable, not broken, not folders or packages) show the **image instead of the icon**, in the same box (List 16 px, Icons 48 px), aspect ratio preserved and centered (`object-fit: contain` in a square box). The category icon shows until the image has loaded and stays if loading fails.
- Served by a custom URI scheme `thumb://localhost/<encoded path>?px=<n>&m=<modifiedMs>` registered in Rust (`src-tauri/src/thumbnails.rs`), so the webview never gets read access to arbitrary files: only absolute paths of regular files with an image extension (≤ 256 MiB) are served; everything else is 404/415. `px` is clamped to 16–256 and requested at twice the icon size (32 / 96) for retina. CSP `img-src` gained `thumb: http://thumb.localhost`.
- **Generation: macOS ImageIO** (`objc2-image-io`, spike T1 succeeded; the `sips` fallback was not needed): `CGImageSourceCreateThumbnailAtIndex` with a maximum pixel size, `CreateThumbnailFromImageIfAbsent` and `CreateThumbnailWithTransform` (EXIF orientation applied), encoded as PNG. This covers HEIC/HEIF, TIFF, WebP, BMP, GIF and the camera RAW formats the system can decode. **SVG** files are served unchanged. Results are cached in memory (≤ 300 entries and ≤ 64 MiB, keyed by path, modified time and size); failures are remembered in the frontend so remounting rows do not retry.
- `image` is only a dev-dependency (test fixtures).
- Verified live in `tauri dev` with fixtures made by `sips` (square, 2:1 and 1:3.3 PNGs, JPEG, HEIC, SVG, a text file named `.png`, a `.txt`): all real images loaded in both views with their natural ratio inside a 48×48 / 16×16 box, the fake image and the text file kept their icons, `fetch` returned 200 `image/png` decoding to 64×32 for the 2:1 image and 415 for the text file, no CSP violations.

## Terminal in the context menu

- **"Terminal"** is in all three context menus (file / multi-selection, folder, empty space, and therefore also the `..` row). It always opens the terminal in **the folder Navita is currently showing**, never in the right-clicked item (action `file.openTerminal`, Rust command `open_terminal`).
- **Which terminal:** macOS has no explicit "default terminal" setting, so Navita uses the application registered to open `.command` shell scripts (UTI `com.apple.terminal.shell-script`, changed in Finder via Get Info ▸ Open with ▸ Change All), read with `LSCopyDefaultRoleHandlerForContentType`; if there is none it falls back to Terminal.app (`com.apple.Terminal`). On the development machine this resolves to Terminal.app (iTerm and Ghostty are installed but not the handler).
- **Every click starts a new instance:** `open -n -b <bundle id> <folder>`. Side effect to be aware of: each click launches another process of the terminal app (a separate Dock icon, quit it separately); dropping `-n` in `terminal.rs::open_arguments` would instead open a new window in the already running terminal.
- Verified live in `tauri dev`: with another item selected, the action started two separate Terminal.app processes and each shell's working directory was the folder Navita showed.
